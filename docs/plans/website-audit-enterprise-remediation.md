# Enterprise remediation and retest implementation contract

Status: design contract for P6; no remediation capability shipped. This extends [the enterprise roadmap](website-audit-enterprise.md) and [spec](../specs/website-audit-enterprise.md). The authorized public pilots remain read-only. Developing the product does not authorize editing those customer sites.

## Verified integration constraints

- `enterprise-report-model.mjs` validates customer reports and digest-bound independent decisions using `validateEnterpriseReport` and `enterpriseReviewTargetDigest`. A finding must reference a failed check and evidence. Decision acceptance is distinct from authorization to mutate.
- The customer report deliberately reduces entity identity to `entityId/type/customerId/runId`; it cannot establish an asset URL, repository, deployment environment or account. Bind the complete source run by `enterpriseDigest(run) === report.sourceRunDigest`, then require explicit host-confirmed mapping of each entity to an asset/environment. A digest is consistency, not authentication.
- Report v1 actions support `proposed` only. Preserve existing artifacts and schemas; change-plan and execution/retest receipts are separate versioned artifacts. No mutation of a historical finding into a resolved finding.
- `authorizeAction` in the bundled authorization library already binds the full session grant to trusted host authorizations, customer/environment/asset/identity/action, validity and operation mode. Reuse it at execution time; never trust a grant loaded from the plan or imported evidence. Expiry blocks execution but does not erase historical evidence.
- At the design checkpoint no remediation implementation existed. The draft source binder below is now implemented; acceptance policy, execution preparation, sandbox, retest, views/CLI and packaging remain open. P6 is not complete.

## Artifacts and trust boundary

Development starts under `scripts/enterprise-remediation/` with repository tests; packaging into the skill requires an explicit candidate version and fresh Codex/Claude Code archive installs. Do not change a released component digest in place.

A change plan is JSON source of truth with deterministic Markdown/HTML views, using the existing report escaping/brand conventions where compatible. It contains `schemaFamily`, `schemaVersion`, `planId`, `createdAt`, `customerId`, `reportDigest`, `sourceRunDigest`, `entries`, and `limitations`. No clock is consulted during rendering. Every entry has:

- `changeId`, original `findingId/checkId`, finding review target digest, and source evidence IDs/digests;
- `entityId`, explicit `assetId/environment`, binding digest and the trusted mapping's reference (not an imported authorization);
- `ownerRole`, rationale and exact proposed artifact hash, plus precondition artifact/revision digest;
- dependencies by change ID, an allowlisted action class, acceptance checks with rule/version/scenario/window, and rollback artifact/precondition hashes;
- plan-time eligibility/gaps and data requests. Drafts may exist without permission; draft creation has no external effects.

Exact-artifact approval is a host-supplied record, never a Boolean or a record trusted because it appears in an import. Required fields are approval reference, approving actor/session, plan digest, change ID, action class, customer/asset/environment/identity, patch digest, base revision/digest, rollback digest, grant time, expiry or explicit session validity, and revocation state. Its exact contents must match the current trusted host record. A broad action grant and an exact-artifact approval serve separate checks; both must be valid.

The host provides trusted asset bindings and authorization separately at execution. An imported plan cannot name itself trusted. Bind the approval to the exact plan/patch digest: a changed patch, base revision, target environment, or dependency requires revalidation. Do not automatically expire an otherwise valid user grant because the chat changed.

No raw shell, arbitrary endpoint, executable script or instruction from report content is dispatched. Host adapters expose only registered operations. The first sandbox adapter is restricted to explicitly allowlisted inert fixture files under one host-selected root. Reject absolute paths, parent traversal, symlinks at every path segment, out-of-root destinations and executable/configuration hooks. Check the current file digest immediately before an atomic write; do not resolve a trusted path and then reopen an unchecked replacement. Other asset classes require separately reviewed host adapters; the initial sandbox does not claim production execution support. Patch bytes are data for a constrained patch adapter; commands found in page content or recommendations are never executable instructions.

## Interfaces and sequence

1. `planChanges({report, sourceRun, proposals, trustedAssetBindings, assessmentAt})` validates the report and run, resolves each finding/check/evidence and exact review digest, and returns a draft plus gaps. Missing review, mapping, current precondition, rollback or acceptance policy prevents readiness, not report generation. Reject duplicate change IDs, unresolved/cyclic dependencies and cross-customer bindings. A plan cannot be marked ready merely because fields are nonempty.
2. `prepareChange({plan, changeId, hostContext, currentPrecondition, dependencyReceipts, now})` revalidates plan digest, explicit host mapping, accepted finding/check review, exact patch approval, operation mode and `authorizeAction`. Returns an inert allowlisted dispatch descriptor or a denial. It does not itself execute an operation. Read-only audit cannot apply, publish, deploy or transact.
3. A host execution adapter consumes only the prepared descriptor after rechecking relevant preconditions immediately before action. The descriptor is not a bearer authorization: re-run `authorizeAction` and exact-artifact approval binding at the actual action time, including current expiry/revocation/identity/asset/environment and patch/base/rollback digests. A queued descriptor prepared before expiry does not authorize execution afterward. It records attempt/result, plan/change/patch digests, target environment, before/after revision, host identity and timestamps. A receipt is not trusted solely because it hashes itself. Interrupted/partial operations are explicit; retry requires inspection of current state and idempotency semantics, never blind replay.
4. `verifyChanges({plan, executionReceipt, retestEvidence, trustedExecutionReceipts, trustedRetestBindings, assessmentAt})` checks artifact binding, environment, observation time, freshness and the original acceptance predicates. Execution receipts and retest evidence have separate trust bindings. Each trusted retest binding identifies the host-observed source receipt and artifact digest, evaluator/rule version, policy and exact check scope, observation time, and evaluator result digest. Recompute applicable deterministic predicates from source artifacts; never accept a supplied `pass` field as a verified result. Imported observations without host verification remain explicitly supplied/unknown for resolution. Each check returns pass/fail/unknown with evidence. No execution proof or missing retest yields unknown. Test success on staging is a staging result; production remains unresolved. A new report revision may reference this result while retaining original findings/history.
5. Rollback is a separate authorized action with current preconditions, not a fallback shell string. Verify rollback with its own evidence. Failed/unknown rollback never becomes a restored state. Where rollback cannot be automatic, record the operator procedure and keep automatic execution ineligible.

## Retest semantics

Retest identity preserves rule/version/entity/scenario/policy bindings. The plan freezes an explicit baseline-window → retest-window mapping before execution, including timezone, duration, lag/waiting policy, cohort/filter definitions and minimum completeness. Point-in-time technical checks declare point observation semantics; period metrics require a new post-change window. A different or immature window is unknown rather than silently accepted. Rule or policy changes require an explicit reviewed change, not an implicit equivalence. Label such results reassessed under changed criteria; they do not automatically resolve a finding under the original criterion. New evidence must follow the execution being assessed, be fresh at assessment, and match the exact target/environment. Same bytes alone do not prove a new observation. A changed timestamp alone does not authenticate recapture.

For finding resolution require all mandatory acceptance checks to pass, no conflicting check evidence, and independent review where the original release contract requires it. Failure remains open; missing/incomplete/stale/contradictory data remains unknown. Excluded or newly N/A checks need an explicit reviewed applicability decision and must not be counted as passes. No before/after conversion or ranking difference is described as causal uplift without a separate experiment design.

Cross-environment migration is an explicit dependency: a staging retest may permit a separately authorized production deployment; only production evidence can resolve the production finding. A successful tool exit is not proof of deployed bytes, provider ingestion, or business outcome.

## P6.1 draft source binder

`scripts/enterprise-remediation/change-plan.mjs` now creates deterministic, private draft plans from a validated report and its full source run. It checks source digest, exact check structure, recomputed source check-context digest, and evidence binding metadata before carrying review digests forward. Host-confirmed asset mappings bind the full source entity digest and explicit target environment. Missing review/mapping/artifact/rollback or expired source evidence becomes a concrete owner-directed request. Duplicate/unresolved/cyclic dependencies are rejected. No imported grant is read and every entry remains draft with executionAllowed false.

Independent code review reproduced two defects: spreading complete source evidence leaked private content, and a valid report could claim review of evidence different from the source run. Regressions reproduced both and fixes project explicit metadata and compare source/check/context bindings. No raw source label, embedded content or extra payload field is copied. A plan digest provides consistency, not authentication or mutation permission.

This is a source-binding foundation, not completion of P6.1: acceptance policy/window mapping, full versioned artifact schema and import validator, action/patch approval and runtime lifecycle remain unimplemented. The planner deliberately requests acceptance policy instead of inventing predicates from recommendation prose. It does not offer an executable or release-ready plan.

## P6.2 inert execution preparation

`prepare-change.mjs` reconstructs a draft from its source inputs using current host-supplied asset mappings and acceptance policies, then compares the complete plan including its digest. The imported input cannot promote its own mapping or policy into host trust. Missing requirements, unresolved dependency receipts, stale source evidence, a changed base digest or a started retest window deny preparation.

For the initial apply-patch operation, both an exact-artifact approval and an action grant must be current. Approval binds plan/change/customer/asset/environment/identity and patch/base/rollback digests, approver, session and validity/revocation. The existing `authorizeAction` evaluator rechecks operation mode and grant at the supplied current time. A read-only grant or audit/plan/verify mode cannot prepare mutation. Duplicate approval or grant references are denied.

A prepared descriptor remains executionAllowed false, requires verification of actual artifact bytes and an execution-time recheck, and contains no shell command or executable payload. This function has no filesystem/network side effects. It does not authenticate artifact bytes, authorize a later queued action, execute a patch, verify dependencies, or produce a retest/rollback result. Those adapters and gates remain open. The initial preparation supports apply-patch only; no publish/deploy/transact dispatch is advertised.

## P6.4 receipt-scoped retest verification

`retest.mjs` reconstructs the plan against host-current mappings/policies and validates an execution receipt separately from a retest evaluator binding. The exact execution receipt must exist in trusted host state; a supplied receipt alone is insufficient. Retest trust binds the entire evidence record and evaluator ID/version, including source digest, scope, check, policy/profile versions and outcome. The host must have verified acquisition and evaluation before registering that binding; this module does not authenticate source systems from JSON or recompute every module predicate.

Verification compares customer/asset/environment, plan/change/patch/base/after-state digests, execution ordering, source freshness at execution, frozen check/policy/profile identity, filters/timezone/completeness and retest window. Point observations must be in their declared interval; period evidence must be captured after the complete period and ingestion lag. Expired/future/early/partial/mismatched evidence is unknown. Failed or rolled-back execution cannot become optimization success. Host verification context must itself match the customer/target; a regression reproduced and closed that missing comparison.

The result is explicitly receipt-scoped: pass means pending-independent-review, fail stays open, unknown remains unverified. It does not mutate historical reports, resolve an entire finding, attest execution authorization or claim business uplift. A late observation cannot turn previously early-collected period evidence into mature evidence.

Independent code review passed 49 focused cases at its snapshot and found no blocking false-pass within this narrow receipt scope. It identified two remaining integration gates: technical SEO scenario IDs include window scope and therefore require explicit reviewed scenario/window mapping for real retests; final resolution must inspect the full relevant evidence set for contradictions rather than one selected receipt. These gates remain open, along with executor, source-evaluator adapters, rollback verification, report revision linkage, views/CLI, packaging and commercial evaluation.

Final verification: 15 retest cases and full 118 files / 1,358 tests passed, with formatting, lint, typecheck, build, site typecheck and 19 site tests. Shared preparation fixture extraction preserved prior tests. No release archive, source website, deployment or customer report was changed.

## Explicit reviewed scenario mapping

Acceptance policies may now include a digest-bound `scenarioMapping` with original scenario, intended retest scenario and review rationale. The binder compares the original identifier with the source check. Without this mapping, retest still requires the original scenario identifier. No implicit rewrite is performed when a new observation window changes a technical adapter's scenario ID.

A mapped identifier only authorizes interpreting the receipt in that declared scope; it does not prove that device, consent, state or other semantics are equivalent. When the scenario identifier changes, the retest output records both IDs, scenarioEquivalence not-verified and findingResolution original-scenario-unverified, even if the receipt's predicate passes. Original-scenario resolution therefore still requires source-adapter equivalence evidence and independent review. Complete contradiction checking remains open.

Independent review passed 52 focused cases at its snapshot and found no unsafe promotion. It identified rejection of existing scenario labels containing spaces/Unicode; a failing regression reproduced this and the binder now reuses the enterprise nonempty-string scenario contract without normalization. Mapped policy fields are optional; older policies without mappings retain their same-scenario behavior.

## P6.4 complete-set contradiction gate

`retest-set.mjs` evaluates every member of an exact host-attested receipt inventory for one change, acceptance policy, target, observation window and assessment cutoff. Missing/extra/duplicate records cannot be omitted from accounting. Each member goes through the receipt verifier. Pass plus fail is a conflict and returns unknown; any unverifiable member or unresolved mapped-scenario equivalence prevents aggregate pass. An all-pass set still requires independent review; no original finding is rewritten or automatically resolved.

The inventory must be registered separately in trusted host state and be the sole canonical inventory for its exact scope/cutoff. Independent review reproduced a loophole where a second registered subset inventory could hide a known fail; a failing regression demonstrated it and canonical-snapshot uniqueness now rejects that ambiguity. This deliberately rejects duplicate same-scope inventories even if membership matches; the host collector must provide one canonical snapshot, with history stored separately.

Completeness is only as strong as the host inventory collector's verified enumeration. This evaluator cannot discover evidence withheld from that collector, and the actual source/evaluator/inventory acquisition adapters remain open. The result labels coverage complete-as-host-attested, includes individual statuses/counts and preserves business uplift as not assessed. It covers the declared change/check, not all website findings or all potential scenarios.

## P6.3 POSIX sandbox filesystem primitive

Ruling: prototype a descriptor-relative Python standard-library backend for the optional development sandbox. Python is not added to a released skill/package, and its availability is not assumed on either supported host. The current local capability probe confirmed Python 3.15.2 / Darwin with directory-relative open/rename/unlink and no-follow/directory flags. Other runtimes/platforms require capability checks and separate validation before packaging. No pip dependency, arbitrary shell command or new supported agent host is introduced.

`sandbox_file.py` opens each root path component without following symlinks, binds the approved directory device/inode and owner/private mode, and operates only on fixed inert `fixture.txt`. It rejects executable/nonregular/multiply-linked targets, bounds input/output bytes, uses a nonblocking cooperating-writer lock, verifies the original and staged bytes after a trusted authorization callback, and replaces via directory descriptors. A staged hash/inode/mode mismatch prevents commit. The callback is a trusted host prerequisite, not permission supplied by imported data. This primitive is not yet wired to `prepareChange`, real host session grants or durable execution receipts.

The backend uses [Python descriptor-relative file operations](https://docs.python.org/3/library/os.html#os.open) and [atomic replacement](https://docs.python.org/3/library/os.html#os.replace). Atomic replacement is not atomic compare-and-swap against arbitrary same-UID mutation. The supported sandbox must be exclusively host-owned, with cooperating writers serialized. The primitive does not promise protection from an adversarial privileged/local process changing the directory concurrently. `valid_until` is an absolute Unix-seconds commit-authorization expiry, not a hard deadline on callback/I/O/fsync; Node process supervision and recovery remain required.

Independent review reproduced three concrete defects: FIFO blocking before file-type validation, lock leakage when staging cleanup failed, and an interruption after rename being misreported as an ordinary pre-write failure. Regression tests reproduced these. Opens now use nonblocking flags; lock closure runs unconditionally even if cleanup fails, preserving the original denial and marking sandbox_cleanup_incomplete; the rename-attempt boundary conservatively classifies subsequent failures as OutcomeUnknown. The caller must inspect/recover an unknown outcome, not retry blindly. No rollback success is inferred.

Fifteen native unit cases passed, including approved replacement, precondition/authorization expiry/denial, symlink root/leaf, wrong root identity, hardlink/executable target, target/staging mutation, FIFO, concurrent cooperating lock, cleanup failure and post-commit interruption/fsync failure. Test command: `python3 -B -m unittest discover -s tests -p test_remediation_sandbox.py -v`. Unsupported non-POSIX test hosts explicitly skip this optional backend; a skip is not platform validation. Node orchestration, actual artifact approval at commit, process timeout supervision, receipt persistence, rollback and native-host integration remain open.

Final repository verification for this optional primitive: 119 files / 1,371 Node tests passed, with formatting, lint, typecheck, build, site typecheck and 19 site tests. The 15 native sandbox cases passed separately. No production file, deployment, release archive or component lock was changed.

## P6.3 supervised development sandbox

The Node executor creates only a new private inert fixture, registers its exact object as an in-process capability and requires the literal sandbox environment. Existing customer roots and production-labelled targets cannot be registered. It checks the approved UTF-8 artifact, prepares against current host state, launches a fixed isolated Python worker and refreshes the host authorization immediately before commit. The worker cannot extend the original expiry. A process watchdog kills stalled execution and waits for close before returning an unknown outcome requiring inspection.

An applied receipt binds the plan, customer, asset, approved bytes and verified before/after hashes. Receipt persistence, rollback, production adapters and native-host integration remain open. This prototype is outside the released package and does not authorize modifying pilot websites.

Independent review reproduced a null-entry lookup leaving a spawned worker alive, and a worker cleanup failure reporting denial after mutation. Launch inputs now serialize before spawn, lookups tolerate unrelated null entries, and post-write failures retain unknown outcomes. The filesystem writer retains a commit-attempt flag before rename, so the worker also preserves unknown status across asynchronous return-boundary interruption. Platform-dependent integration tests explicitly skip absent Python/POSIX capabilities; skips do not establish platform support.

Verification: full repository checks passed with 120 files / 1,379 Node tests, formatting, lint, typecheck, build, site typecheck and 19 site tests. After the final Python interruption-boundary correction, the 8 Node executor integration cases passed again and independent review passed 18 native cases, including injected KeyboardInterrupt, SystemExit and OSError after actual replacement. No remaining concrete blocker was identified within this bounded sandbox scope; this is not production execution readiness. No release archive, component lock or deployment changed.

## P6.3 attempt lifecycle and unknown-outcome quarantine

A registered sandbox capability now serializes execution and disposal. Once a worker launch is attempted, its plan/change pair is consumed even if the outcome is denied; a new approved plan is required for another attempt. Successful execution cannot be replayed by resetting the fixture bytes. Unknown outcomes quarantine the entire capability, so changing the plan or grant cannot silently bypass inspection. There is deliberately no reset/unquarantine API yet. Explicit disposal remains available after the worker closes and is not proof of recovery or rollback.

The disposal flag is set before its first asynchronous filesystem operation; execution cannot race into a root being removed. Execution remains in flight until child close, including timeout/kill paths. A synchronous runtime launch failure returns unknown and quarantines conservatively. Invalid inputs rejected before launch do not consume an attempt.

Three regression cases first failed against the previous executor and then passed: retry after timeout, concurrent execution/disposal, and replay after a successful write with manually reset bytes. This is an in-process guarantee for factory-created, non-reconstructible capabilities. It is not a durable cross-process attempt ledger, authenticated receipt store, recovery inspector or production idempotency implementation; those requirements remain open.

Independent review found no blocking lifecycle defect and independently passed 11 focused integration cases. Final verification passed 120 files / 1,382 Node tests, format, lint, typecheck, build, site typecheck and 19 site tests. No Python backend or released package changed in this increment.

## P6.3 durable sandbox attempt journal

The optional Python worker now requires attempt metadata, including UUID, plan/change, customer and asset-binding digest. Node generates the UUID before launch, uses it for the applied receipt ID and returns it with the deterministic journal key on every post-launch outcome, including unknown and subsequent quarantine responses. An ID can exist without an admitted intent if launch fails before persistence; it is correlation, not proof of admission.

Under the existing cooperating-writer lock, the backend scans at most 256 root entries and permits at most 100 retained attempts. It validates reserved filenames against their plan/change content, UUID uniqueness, exact schemas, root identity/fixed target, before/after hashes, timestamps and intent-to-result digests. Reserved records require descriptor-relative no-follow/nonblocking regular single-link owner-private files bounded to 8 KiB. Pending, unknown, malformed, orphaned or incomplete-publication state blocks all new admission. Completed plan/change keys cannot replay even after the target bytes are reset and a fresh process starts.

Intent is published before staging or the fresh authorization callback. Journal writes first fsync a private staging file, exclusively link it into the final name, fsync the directory, remove staging and fsync the directory again. Final records are never overwritten or deleted by the backend. A leftover journal stage or multiply-linked final file blocks further attempts. Terminal applied is recorded only after replacement, target directory sync and hash readback; denied means this attempt did not cross the rename boundary, not that external actors left the target unchanged. Post-rename exceptions record unknown when possible; interrupted/missing terminal records remain pending.

A lost acknowledgement can leave Node's outcome unknown while a valid applied terminal exists on disk. No automatic recovery or replay is inferred from either state. An inspector must distinguish verified historical mutation from caller receipt delivery and current file state. Journal data is not an authorization, a self-authenticating acquisition receipt or an automatically trusted retest registration.

Persistence applies while the private root is retained. Explicit disposeSandboxTarget still removes the whole sandbox, including its journal, after the worker closes; disposal is not rollback or recovery. The low-level legacy primitive remains available for isolated development tests, but the Node worker rejects missing/null metadata instead of using that fallback. Existing-root adoption, host identity restoration, production execution, recovered receipt registration and rollback remain open. Future adoption must bind customer/asset identity through separately trusted host state.

Regressions cover null worker metadata bypass (red then fixed), killed worker pending intent followed by a fresh process, intent/result persistence failures, post-rename and post-link interruption, malformed/orphan records, modes/identity, duplicate attempt IDs and bounded enumeration. Node integration also verifies receipt/intent correlation and intent presence before fresh authorization. These are crash/fault injections on the tested POSIX runtime, not cross-platform or power-loss certification.

## P6.3 read-only sandbox inspection

inspectSandboxTarget accepts only an existing factory-issued capability, supervises a fixed isolated Python inspection worker and returns a private point-in-time observation. It holds the capability busy until worker close, including timeout/protocol/output failures, so disposal and execution cannot race the inspector. The worker has a 1 MiB output budget and the caller-selected bounded process timeout. It does not adopt a root supplied by imported data.

The backend opens an existing private regular single-link owner lock read-only and takes a nonblocking shared lock; missing or busy lock yields unknown without creating files. It reuses the full journal validator with an inspection-only allowance for valid pending and unknown outcomes. Admission still rejects those outcomes. Orphaned/malformed records or publication remnants invalidate the entire observation. All 100 retained attempts remain inspectable even when the admission budget is exhausted.

Each returned record preserves historicalStatus and commitAttempted independently of the current target digest. Pending commitAttempted is null, not false. Current hash relations are matches-before, matches-after, matches-both or matches-neither; none promotes history into success. Applied history with current drift remains applied history plus drift; pending with matching-after bytes remains pending. The observation reports no artifact contents and issues no receipt or finding resolution. Node preserves callerOutcomeUncertain and the last attempt correlation without changing the capability quarantine or consumed-attempt set.

The read-only contract excludes application writes, repair, chmod, cleanup, lock creation and journal updates; normal filesystem access-time bookkeeping is not a claim of zero kernel metadata activity. Consistency assumes the same exclusive host-owned root and cooperating writers as execution. Observation time does not guarantee the state remains unchanged after the shared lock is released. There is no automatic recovery decision or existing-root adoption/production inspector.

Independent review passed 43 native and 17 Node focused cases and found no blocking defect in scope. Tests cover unchanged bytes, absent/busy lock, malformed sibling, mixed pending/applied history, matching-before unknown, matching-after pending, identical before/after hashes, full 100-attempt capacity, imported-target rejection, persistent quarantine and timeout/disposal coordination. The initial six native inspector tests failed before implementation; the shared validator refactor preserves all previous execution/journal regressions.

Final repository verification: 122 files / 1,403 Node tests passed, plus format, lint, typecheck, build, site typecheck and 19 site tests. The 43 native sandbox cases passed separately. No released archive, component lock, production asset or deployment changed.

## P6.4 rollback preparation and separate authority

prepare-rollback.mjs is a pure preparer for the development sandbox full-text adapter only. It replays the original plan at its original assessment time using host-confirmed pinned source bindings/policies, checks an exact host-verified applied receipt, and requires separately attested adapter semantics bound to that receipt digest. Equality of hashes alone does not establish a full-replacement adapter. The rollback artifact must equal the original before image; the declared current precondition must equal the original applied after image. Non-sandbox targets and unsupported adapters are denied.

A separate trustedRollbackApprovals record binds rollbackId, original plan/change, exact receipt ID/digest, action apply-patch with purpose rollback, adapter/fixed target, customer/asset/environment/identity and rollback/current/restoration hashes. It must be granted after original completion and remain current/unrevoked. An active host apply-patch grant in remediate mode is also required. The original apply approval, an inspection observation or an unknown execution outcome cannot substitute for these records. No bundled authorization action enum is changed.

Timing ruling: fresh rollback authority may restore a verified prior image even after an original apply completed outside its planned evidence/retest window. Basic chronology remains mandatory: plan creation <= original start <= completion <= rollback assessment. originalTimingWithinPlan is a deterministic diagnostic bound through the approved plan/receipt, not original authorization proof or a reason by itself to deny restorative rollback. The receipt schema does not contain original grant/approval proofs, so originalAuthorizationVerified remains false; this means not established by this preparer, not a claim that the original action was unauthorized.

Known dependencies or dependents within the submitted plan are denied. Cross-plan dependency completeness is not inferred. The prepared descriptor remains executionAllowed false and requires physical target/current-byte and artifact verification, complete dependency inventory, durable rollback replay protection, fresh runtime rechecking and restored-state verification. CurrentPreconditionDigest is caller-supplied here, not observed by this pure function. The descriptor binds a logical asset and fixed filename; a future executor must bind the original physical root/capability and original journal attempt separately.

The tests cover approved inert preparation, missing/wrong purpose authority, unknown/forged receipt, wrong environment, drift, missing/unsupported adapter attestation, receipt chronology, active grant/mode, revocation/expiry/session validity, known dependents, exact prior-image requirement and late-apply timing diagnostics.
